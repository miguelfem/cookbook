name: apr
description: Turn solved workflows into reusable CookBook recipes; set up, configure or troubleshoot their connections and execution. For an unchanged known prepared recipe, use the connected MCP tools directly without reloading this authoring skill.
---

CookBook saves solved workflows as callable recipes. Combine code, approved MCP/API/CLI tools, explicit external model calls, optional Jev nodes and parallel jobs. The runtime owns repeatable execution; the caller supplies only the judgment or native capability that the recipe actually needs.

With `apr_project`, connect the current project: `prepare` its absolute root; write the JSON in `verification_contents` to `verification_file` using the client's authorized file tool, preserving all fields and values; `connect` with `challenge_id`; remove `cleanup_file`. Include the returned `workspace` on every later APR call and reconnect after MCP restarts. Do this yourself. It grants no credentials or native execution; never substitute another folder or use owner commands after denial.

A legacy project-only attachment has no `apr_project`; omit `workspace` because it is already bound to one assignment. Directories and chat titles do not change authority.

Reuse a known immutable `process_ref` and input contract directly. Use `apr_discover` to select a recipe or check an unknown contract. For authoring, read `guide:"overview"` for the capability map and advertised topics, then only the relevant guides. `workflow_design` maps solved work and existing project procedures to execution owners; `authoring` covers registration; `execution_review` audits boundaries. `connections` covers external model APIs and reusable MCP/API tools; `adapters` covers CLI/SDK wrappers; `jev` covers Choice/Score/Noul nodes; `routing` covers composition and parallel batches. Scheduled/computer-use work and optional improvement/learning have separate guides. On an older server, use only advertised topics.

Before authoring, read its guide for connection, credential, schema and execution rules. Jev availability, configuration and authorization are separate; other model APIs do not require it. Author only with current file access; missing access permits no settings or owner commands.

Reference-first: complete the workflow with authorized tools or inspect a permitted accepted reference, then derive and test its reusable recipe. Preserve actual inputs, outputs, checks, source/artifact references, variable inputs and unknowns. CookBook does not compile traces automatically. Use `workflow_design` to map every requirement and `execution_review` to compare actual caller work, including work inside handoffs. A handoff covering an entire workflow is not evidence of one model call. Preserve quality and authority when replacing covered manual instructions with recipe calls and verified receipts.

Preflight during preparation or after input/access changes; skip setup for an unchanged prepared contract. Start with `apr_run`. Use succeeded, untruncated output directly. Inspect only unfinished or truncated work with `apr_inspect {"view":"run","run_id":"..."}` and `detail:true` when needed. Use advertised `result_view:"output"` for complete values without progress metadata. Use `"receipt"` when the saved run will be viewed outside the chat. Preserve the process pin, semantic input and config. Retry the same lost start with the exact request key; use a new key for new work.

Make one bounded composed workflow the default for one objective. Reuse existing helpers; keep intermediate data in artifacts and declare real dependencies before batching. Inspect a known connection directly; discover alternatives only when needed. Builtins are pure; trusted Python retains `effect:"write"`, one attempt, bundled source, a result schema and matching capability. Use evaluated Jev/model nodes for residual semantic work, with explicit caller review for unresolved judgment. Select confidence thresholds from evidence for the exact question/model, not convention.

For caller handoffs, use only tools available here. Submit observed results with saved identity and a stable submission key; never fabricate success. Other applications' tools and credentials remain unavailable. Keep the root run ID and pending capability: the service owns accepted work; closing the client does not cancel it, and waiting does not wake it.

Keep credentials in protected owner bindings, outside chat, recipes and tool arguments. Do not read/import private attachments or expose live handoff tokens. New connections, paid calls and schedules require user authorization; a proposal is not approval. Native scripts are trusted host code, not sandboxed. Report measured results, unknown costs and blockers.
