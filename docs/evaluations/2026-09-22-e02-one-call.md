# E02 follow-up — results in one recipe call

Status: **all six client outputs accepted; one-call behavior passed; client speed
target still failed**. Small recipes now return completed output from `apr_run`.
The packaged MCP path took 103–121 ms in separate model-free probes. Fresh Codex
sessions still took 78.398 seconds in total versus 62.608 seconds for direct
Luna-low, with CookBook slower in each pair.

This preserves the [original E02](2026-09-22-e02-reuse.md) and
[previous prepared-reuse pilot](2026-09-22-e02-prepared-reuse.md). Different
holdouts and variable client timing prevent attributing historical aggregate
changes solely to this patch.

## Method and change

Three new synthetic invoice-readiness cases and a separately authored deterministic
oracle were frozen before prompts. The oracle was not human reviewed; this is
not E05. The lead separately recalculated the oracle, regraded all six outputs
and verified the frozen file hashes after execution.

Both arms used fresh Codex CLI `0.155.0-alpha.9.2` sessions, `gpt-5.6-luna`, low
reasoning, normal `--approve-for-me` review and a 180-second/12-call bound. Order
was direct/CookBook, CookBook/direct, direct/CookBook. Direct agents retained normal
shell/scripting access. CookBook registration, Python permission, fixed run
attachment, preflight and service startup happened before timing. The exact recipe
reference was supplied. Neither onboarding nor discovery occurred during timing.
No external provider was called.

The patch waits briefly after durable acceptance, reading through the scoped
service. Ready output returns in the original call. Longer work keeps its run ID;
caller handoffs, strict permissions, retry keys and response limits remain intact.
Descriptions and installed guides teach direct reuse and required inspection
arguments. No client approval policy was changed.

Each CookBook session made one task-file read and one `apr_run`; all three run
responses already contained exact, untruncated output. There were **zero
inspection calls**. Full client wall was 25.2% higher than direct, and reported
noncached input was 27.8% higher. Cached tokens are a subset of input; dollars and
approval-review model usage were unavailable.

The recurring CookBook task-file reads occupied 4.635–10.831 seconds in client
events; `apr_run` events occupied 5.434–10.946 seconds. These are client event
intervals, not pure filesystem or MCP execution. Time outside recorded tool events
also includes unisolated client work. We cannot separate approval review, model
processing, scheduling and startup from these traces alone.

Aligning the harness UTC start/event clock with saved service timestamps places
**5.306, 10.798 and 6.270 seconds** between the Codex tool-start event and durable
`run.created`. The client completion events follow `run.succeeded` by approximately
6.3, 1.8 and 28.1 ms. Small cross-clock alignment error is possible. This locates
most of the tool-event delay before durable acceptance; it does not distinguish
approval, bridge startup, dispatch or queuing within that interval.

Three separate warm, model-free stdio MCP calls returned complete output in
**103.165, 112.821 and 120.794 ms**, including the service execution. Initialization
took 5.890 ms separately. These probes exclude the Codex client path. Each arm
and probe read each synthetic source once. No failed case was replaced or retried.

## Decision and evidence

The unnecessary inspection/model round trip is fixed. The remaining measured
gap is dominated by the client path around a short local operation. Next work
should reduce recurring contract/tool context and isolate client dispatch latency;
speeding up the Rust worker is unlikely to remove seconds of client overhead.
Any narrower recipe interface must retain the same permission checks and honest
effect annotations. This is a next investigation, not an implemented feature.

Fresh sessions reread the task contract in both arms. This pilot does not measure
successive calls inside an already-open prepared conversation, and it does not
test a stronger model with reduced reasoning. Three cases do not establish broad
performance or economic savings. Same-user filesystem access was not hard oracle
isolation. Total manual setup time was unmeasured and excluded.
