# Local runtime for agent-authored processes

Design proposal, 14 September 2026. No implementation or product name has been selected. Miguel confirmed that the system should support both independent execution and explicit pause/resume for steps performed through the calling agent's existing tools.

The proposed product lets an agent create a reusable process, bind its configuration, test it, and expose it to the relevant project or assignment. The runtime executes repeatable operations and stores progress. AI remains responsible for creative or interpretive decisions. Rust is a reasonable implementation choice for the local core; lower token consumption depends on the interaction design, not the language.

**The experience should start with an assignment.** A user asks for a result. The agent searches the processes already available in that assignment. It reuses one or creates a definition with executable steps, input/output schemas, pinned dependencies, and requested capabilities. The runtime checks the definition and reports missing configuration or access in a structured response. Within access already granted to that assignment, the agent can test, register, and run its process without further manual setup. New access is resolved at that boundary rather than rediscovered during every run.

The agent's generated code and manifests request permissions; they cannot grant themselves permissions. Validation and passing tests are useful evidence about behavior, not permission to access additional projects or credentials.

**Use Rust for the supervisor, while keeping process authoring accessible.** The first implementation can consist of a Rust local service, a CLI and MCP adapters over the same internal API, SQLite for execution records, and files for larger artifacts. The service starts on demand and owns jobs independently of a particular conversation connection. It needs no separate database server. Its storage and IPC access are restricted to the local user.

Processes should initially use ordinary scripts in one supported language plus a small structured step manifest. Python is a practical first adapter for ordinary automation scripts; choosing it is an MVP proposal, not a universal preference. Pin the interpreter and dependencies. The supervisor can be one binary, but a Python or JavaScript executor adds its own installation and memory footprint. Do not market the whole installation as dependency-free. Avoid supporting several languages, a new programming language, and a visual workflow editor in the first release.

**Project and assignment scopes must be enforced.**

| Scope | Purpose | Lifetime and access |
|---|---|---|
| Personal library | Reusable process templates | Persistent; a project explicitly imports a pinned version. Importing code grants no credentials. |
| Project | Project processes, defaults and connection bindings | Persistent; accessible to callers bound to that project. |
| Assignment | Tools, permitted paths, connection access and overrides for one task | Temporary; closing the assignment revokes new actions and pauses unfinished work at a safe boundary. |
| Run | Frozen code/configuration references, inputs, attempts and results | Retained for diagnosis and deliberate resume, subject to a separate retention policy. |

A trusted client attachment binds project and assignment identity. A model-supplied project ID cannot switch that attachment into a different project's authority. Discovery filters the catalog and execution independently checks authorization. A folder name, namespace or working directory alone is not an isolation mechanism.

**Both execution modes share the same saved run.** Ordinary steps execute locally or call an authorized external API. A step requiring the current agent's capabilities transitions to `waiting_for_agent` and returns a compact request: run and step identifiers, required action, relevant artifact references, expected result schema, and a scoped continuation token. The agent uses its own tools and submits the observed result. The runtime validates that response and continues.

This makes an image workflow possible without assuming that the Rust process can directly invoke the image tool in a conversation. Each supported agent client needs an adapter, skill, or integration that performs the handoff. If the agent disconnects, the request remains pending; reconnecting should discover it without polling an unchanged run through a reasoning model. An unattended run can only perform AI steps for which an independently callable provider or worker has been configured. Provider API billing is separate from whatever access the caller's subscription provides.

**Expose a small, stable interface.** Ordinary execution needs discovery, run, inspection and resume operations. Process definition, validation and configuration management can be a separate tool set exposed during authoring. Discovery returns short names/descriptions and loads full schemas only for selected processes. A process runs multiple deterministic operations internally before returning. Results default to short status and exceptions, with larger artifacts fetched only when relevant.

This is compatible with both terminal-based agents and MCP clients. Per-assignment exposure need not depend on a client's ability to refresh a changing list of hundreds of tools: a stable discovery/run interface can enforce the assignment filter itself.

**Configuration management and secret management are different capabilities.** Ordinary values such as output directory, locale and endpoint choice can be read and edited by the agent. Resolve permitted defaults in a documented order—project, then assignment, then allowed run overrides—and record the effective configuration for the run. Avoid changing a machine-wide shell environment to configure one assignment.

For secrets, expose names, availability, connection status and binding operations. The agent can request use of `project/image-provider`, while a secure local flow or supported credential provider handles initial entry and rotation. Record references and versions rather than plaintext in manifests and logs. Rotation or revocation may require a paused run to be rebound explicitly; freezing a run does not guarantee an old credential will remain usable.

Passing a secret into generated code as an environment variable gives that code the secret. Hiding it in the UI or redacting logs cannot change that. For a protected-credential mode, the executor must be constrained and the runtime should perform narrowly authorized authenticated requests on its behalf. A trusted local-script mode may support direct environment injection, but must describe that weaker boundary honestly. Both modes still need limits on the operations an authorized credential can perform.

**Reliable resume is the difficult engineering work.** Freeze process versions for active runs; edits produce new versions. Save step inputs, outcomes and artifacts at explicit boundaries. A duplicate continuation should reuse a recorded result or be rejected. Validate types and required files, keep external effects separate from pure transformations, and return failures in a form the agent can act on.

An external request can succeed immediately before the runtime loses its response. Persisted state alone cannot guarantee exactly-once external effects. Use downstream idempotency keys where supported; otherwise mark the outcome uncertain and reconcile it before retrying. Cache only operations whose reuse conditions are known. Do not treat image generation or a state-changing API call as a safe cacheable function by default.

Native subprocesses are not sandboxed merely because the supervisor uses Rust. The first prototype can be explicitly limited to trusted local scripts. A broader product that runs arbitrary agent-generated code needs a selected and tested isolation backend before it claims enforced filesystem/network/secret boundaries. Deno or WebAssembly are possible directions, each with compatibility and footprint trade-offs; unrestricted subprocess or native-library access can defeat the intended boundary.

**A first prototype should prove three properties.** Use a file/report process to show unattended deterministic execution, a document review/export process to show pause/resume into the agent, and a scoped API process to show credential binding. Compare against the same work done through separate agent calls, holding output quality constant. Measure authoring/setup separately from repeated execution; include input/output tokens, agent interactions, retries, image/provider calls, elapsed time, and correctness of results.

The prototype should also demonstrate that a second assignment cannot discover or run unauthorized tools, a disconnected agent can resume the correct waiting step, and a lost response does not blindly repeat an external action. These are proof points for the architecture, not claims of validation already performed.

**Existing implementations deserve a focused comparison before a full build.** [OpenClaw Lobster](https://docs.openclaw.ai/tools/lobster) already covers agent-authored local pipelines, environment configuration and resumable checkpoints. Its [standalone implementation](https://github.com/openclaw/lobster) uses TypeScript/Node; request-input and provider/agent adapters do not establish access to an arbitrary calling agent's existing tools. [Cloudflare Code Mode](https://developers.cloudflare.com/agents/tools/codemode/) covers model-written code, progressive discovery and reusable execution, with a different hosting model, and remains experimental. Its [approval-replay mechanism](https://developers.cloudflare.com/agents/tools/codemode/how-it-works/) does not automatically recover arbitrary interrupted runs. The [official Rust MCP SDK](https://github.com/modelcontextprotocol/rust-sdk) supplies protocol infrastructure. [Deno's permission model](https://docs.deno.com/runtime/fundamentals/security/) and [Wasmtime's security design](https://docs.wasmtime.dev/security.html) illustrate executor trade-offs. These capabilities were checked in documentation and source descriptions, not independently runtime-tested.

The bundle to validate is local installation, agent-driven authoring, explicit project/assignment access, credential binding and caller-tool handoff. Rust supports that product; it is not by itself the product's differentiation. A prototype and comparison against existing tools remain outstanding.
