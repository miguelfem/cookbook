# Recipe execution-boundary review

Recipe authoring optimizes accepted work per caller-model round trip and retained context, subject to the same quality, scope, authorization and effect guarantees as direct work. This is a design objective, not a promise of token savings. The installed skill links to short, task-specific guides so an ordinary author need not read this repository.

The installed `workflow_design` guide translates capabilities into execution
choices and requires an authoring map of observed operations, acceptance checks,
execution owners, inputs/receipts and unresolved dependencies. This map is
reference evidence, not a new manifest or audit field. Migrate covered manual
project instructions along with their execution, within the authorized scope;
preserve their quality and permission requirements and make recovery explicit.
One native-tool requirement does not justify assigning the surrounding routine
workflow to the caller. Count actual model activity within handoffs, and preserve
existing combined helpers when moving them would not remove caller work.

Before generation, inventory the current workflow's **incremental** model round trips, repeated instructions, raw service calls, caller-visible payloads and retained context. A script that already performs a batch is one model opportunity even if it makes many HTTP requests. Classify each operation as deterministic calculation, service operation, bounded classification, open judgment, agent-exclusive tool use or owner decision. Compile deterministic and service work into runtime steps; consider an explicitly configured classifier for bounded classification. Every agent step needs a concrete reason and a bounded return contract. The runtime cannot inherit a calling client's tools or credentials. Missing APR access is a pending dependency for an executable connector recipe and scoped owner proposal, not a reason to turn that service operation into caller work.

Design input and output contracts before the graph. Pass intermediate values by bindings. Page and aggregate within the runtime; preserve full raw data as a retrievable artifact. The normal result carries the next decision, a verified receipt or an actionable exception within a declared byte/schema budget. Context reuse uses stable hashes or revisions; unchanged guidance is reused and a changed revision explicitly lists additions, changes and removals. Reading a giant artifact back into the caller defeats this boundary. One run should cover consecutive routine work, pausing only at a genuine judgment and resuming its deterministic persistence after a submitted result. Long-running work and polling remain service-owned. External writes retain expected-base checks, stable request keys, explicit effect intents, uncertainty and evidence-based reconciliation.

The pure `apr_core::audit::audit_recipe` function accepts an admitted manifest plus optional author review metadata kept outside the manifest. It reports step counts and structured advisory findings for unexplained agent boundaries, routine work described as an agent boundary, missing output budgets and pending connections. This metadata is a review sidecar: old 0.1 and current 0.2 manifests remain unchanged and admission remains authoritative. The audit inspects declared topology and notes; it does not parse instructions into semantic proof, grant access, check live health or enforce a keyword ban. A clean report does not prove equivalent accepted-result quality.

Acceptance must exercise synthetic connector and mixed workflows through disposable runtime state. A deterministic multi-service case should complete with zero caller handoffs even when the caller also has a service tool. Pending connection access should block readiness while retaining executable steps. A mixed case should stop at exactly its declared judgment, prevent downstream effects until a valid result, and resume with idempotent write handling and visible uncertainty. Large pages and raw data must remain retrievable while the normal result stays within budget; conflicts and removed guidance must remain explicit. A protocol fixture establishes structural behavior only. Live model quality and savings require matched accepted work with separate accounting for one-time authoring, repeated execution, main-agent calls, retained input/output tokens, cache/context reuse, raw HTTP calls and any classifier/provider usage.

The installed `execution_review` guide ships the sidecar shapes and complete service, judgment and compact-context examples. Authors invoke `apr_manage {action:"process.audit",path,review}` against project source; the response includes its immutable `process_ref` and an advisory report. This is author-only, reads within the attached project and makes no provider call or grant.
