# Author a CookBook recipe

If `apr_project` is available, connect the current project first: prepare, write the exact temporary verification file with your authorized file tool, connect, then remove the proof file. Include the returned `workspace` on every APR call below. This is agent plumbing; the user needs no per-project setup. Fixed attachments omit it.

A recipe is a saved workflow, not a prompt that replans itself on every run. Reuse deterministic steps for known work and declared rules for exact choices. For reasoning or generation, a recipe can call an approved external LLM API with the user's chosen provider/model, or request the caller agent. Fetch `guide:"connections"` for direct model calls, provider/model selection and billing. Jev is an optional routing provider, not a requirement for other model APIs. CookBook cannot inherit the agent's native tools or connections.

Reference-first is the default for reusable work: complete the workflow successfully with the user's available tools, or start from a previously accepted workflow the user permits you to inspect. Preserve the observed input/output contract, actual tools and steps, checks, source and artifact references, variable inputs, residual decisions and explicit unknowns in a portable reference such as `examples/reference-first/solved-workflow-reference.json`. Derive the recipe from that evidence; there is no automatic trace compiler. Never invent a successful result, provider quality, or external effect. Mark missing evidence unknown and obtain a real observed result before calling the workflow solved.

Before drawing the graph, fetch `guide:"workflow_design"`. It maps capabilities to concrete needs, assigns every observed operation and check to an execution owner, and explains how to migrate existing project instructions. Preserve stable observed work as code or approved connections, with explicit Jev/model/caller nodes for residual judgment. Count actual caller activity inside handoffs; a whole procedure delegated through one agent step still incurs its internal model work. Compare retained cases and outputs, audit, validate and preflight, then run with authorized inputs before reusing the immutable reference.

Do not choose a confidence threshold by convention. For semantic decisions, evaluate representative labeled cases for the exact model, question revision and policy; if confidence is uncalibrated or borderline, route to caller review and record the evidence used for any threshold.

Design the small input/output contract first. Bind intermediate values between steps; paginate or aggregate in the runtime; retain full source data as an artifact with bounded retrieval. Budget the normal return to next-decision data, verified receipts and actionable exceptions. For repeated guidance, carry a digest/revision and return only changes, including removals; an unchanged revision should reuse prior context. An artifact path plus a request to read all raw bytes does not reduce context. Make one bounded composed workflow the default for one user objective; use child recipes only for genuine reuse, independent versioning or separate authorization. Batch repeated independent records with stable `foreach` keys, declare real `needs`, and choose concurrency from idempotency, provider limits and shared budgets. Return artifact references rather than recopying large payloads, and use compact results only when the advertised contract supports them. The service owns long jobs and polling. Preserve expected-base checks, idempotency, uncertain-effect reconciliation and provenance.

1. Discover reusable recipes first with `apr_discover`. Read only a selected recipe's input/output schema with `{process_ref,detail:"schema"}`. For a known connection, inspect `bindings` and its `connection_contract` directly. When choosing alternatives, page `connection_library` using `after:next_cursor` and inspect selected contracts. Record transport, authentication and credential type, required authority and any API fallback reason. Assess official MCP, API and CLI routes and choose the simplest supported contract. Fetch the connections guide and then the adapters guide when a reviewed adapter is needed; do not push technical setup onto the user. For a tool approved across projects, fetch `library_contract` with its `library_id` and `revision`, then use `apr_manage {action:"connection.use",library_id,revision,name}` to bind that exact revision locally. Existing workspace-only grants remain local.
2. For a new recipe, fetch `apr_discover {guide:"schema"}` and the relevant example. `guide:"starter"` includes a complete account-free recipe and sample input; `guide:"routing"` includes exact routing and a caller review; `guide:"jev"` includes the optional provider contract and an example. These guides come from the installed binary, not an online manual or an assumed source checkout. If a reviewed connection name is already known, inspect that contract directly; page the full connection library only when choosing or discovering alternatives.
3. Write `recipes/<name>/process.json` inside the attached project using your current client's authorized file tools. File authoring belongs to the agent; MCP registration does not create source files. Use the returned manifest, adapt names, schemas and steps, and add meaningful fixture inputs. If project file access or `apr_manage` is unavailable, explain the missing attachment/authoring access instead of using owner commands.
4. Call `apr_manage` with `{action:"process.validate",path:"recipes/<name>/process.json"}`, fix admission errors, then call `process.register` with that path. Save the returned immutable `process_ref`. If validation returns an admission diagnostic, use only its allowlisted `field`, `reason` and `repair`; do not infer or expose raw manifest payloads. Fetch `guide:"execution_review"` for review sidecar shapes and complete service/judgment/context examples. Call `apr_manage {action:"process.audit",path,review}` before registration and inspect each finding; the audit reports declared boundaries and budgets, not semantic proof or measured savings. Validation checks structure and semantics; it does not grant connections or prove a live account works. For native scripts, use the owner's pinned interpreter and project-relative frozen source. Test imports using the exact command the runtime will execute; a canonicalized virtual-environment symlink may resolve to an interpreter without its packages. Native code is trusted host code, not a sandbox.
5. Use the discovered input schema, `apr_inspect {view:"readiness",process_ref,detail:true}`, and `apr_run {process_ref,input,config_overrides:{},request_key,mode:"preflight"}` before starting. Explain waiting agent steps, missing approvals and unknown prices. Preflight makes no external dispatch. `process.test` supports only the runtime's fixture operations; a successful fixture is not live-provider evidence.
6. Start with `mode:"start"` only within the user's authorization. The call briefly waits and can return completed output directly; use it without an extra inspection. For unfinished or truncated results use `apr_inspect {view:"run",run_id}` and add `detail:true` when required. Optional `wait_ms` is 0–5000, default 1000; zero returns acceptance immediately. Keep the same process, input, config and request key when retrying a lost response. For a new run use a new key. Prepared reuse of an unchanged reference and input contract does not repeat discovery, guide loading or authoring. Fetch `guide:"handoffs"` when the run needs the caller or an external effect is uncertain.

Use `schema_version:"0.2"` for new routing/composition. Bind inputs with `{input:"/field"}`, prior outputs with `{step:"step_id",pointer:"/field"}`, config with `{config:"/field"}`, or constants with `{literal:VALUE}`. These are JSON pointers, not templates or JavaScript expressions. Every referenced producer belongs in the dependency graph. Pure builtins include `json.write`, `json.select`, `artifact.manifest`, `artifact.validate_set` and `artifact.bundle`; inspect their demonstrated shapes in the examples instead of inventing arbitrary builtin operations. General deterministic computation belongs in an approved frozen Python script, which is trusted host code and must retain `effect:"write"`, one attempt, a bundled entrypoint, result schema and matching Python capability. Use a connector for an approved external model/service, Jev for bounded semantic routing, and a caller handoff for a concrete judgment or agent-exclusive capability. Computer use requires the bounded native scaffold, fresh observations, individual effect intents and explicit completion review.

Keep source manifests, ordinary config and test fixtures free of credentials and live continuation tokens. Large outputs belong in artifacts. Permission failures require an owner decision, not an approval flag fabricated by the agent. The installed schema is a shape contract; the runtime's semantic validator remains authoritative.

For OAuth-backed HTTPS tools, use author mode `apr_manage {"action":"connection.discover","resource":"https://service.example/mcp","client_id":"","scopes":[]}` for public metadata only; add `metadata_url` only when the service documents a specific metadata endpoint. Blank `client_id` selects generic advertised dynamic registration. Discovery never logs in, registers a client, creates a grant or returns a credential. The owner must complete browser login/discovery and approve each operation. Keep saved-account authentication, operation approval and cross-project sharing as separate owner decisions; recipe calls use the caller's CookBook binding and do not inherit native client credentials. Registration authentication is handled by the native credential vault (`none`, `client_secret_post` or `client_secret_basic`).

For new bearer or API-key header proposals, add the exact nonsecret `credential_label` (for example, `generic project API key` or `management token`) so the owner can distinguish the required credential. Never place the secret in recipe JSON or model-visible arguments. OAuth uses owner-managed account metadata instead of a key label.

Compare equivalent accepted work before making a cost claim: measure actual main-agent calls, retained input/output tokens, downstream context reuse, cache usage and any classifier/provider usage. Separate one-time authoring from repeated execution. Structural handoff counts alone are not measured token savings.

Installed guides expose a content-hash `guide_revision`. Reuse unchanged guide content by that revision; always check the separately reported running-service features. A changed guide revision requires fetching its current instructions.

Python approval is persistent per workspace and interpreter. If readiness reports missing Python access, prepare the environment using your authorized tools, then provide its absolute interpreter path and direct the owner to **CookBook Settings → Python recipes**. The owner reviews and approves it once. Do not treat CookBook permission as a Codex shell approval, ask for repeat approval on every run, or grant yourself execution through author MCP. A changed interpreter still requires review; identical reapproval keeps the existing revision. Native Python is not sandboxed.
