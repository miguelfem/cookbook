# E02 — synthetic invoice readiness reuse pilot

Date: 2026-09-22. Internal maintainer-run, account-free macOS ARM64 development-package pilot. **Eight of nine matched heldout executions produced the exact required output:** direct agent 3/3, reusable script 3/3, CookBook 2/3. CookBook's missed case failed at project connection before its Recipe ran; it was retained without replacement. This prevents the three-condition launch quality gate from passing on this cut. The nine-case result is exploratory and does not establish savings or population reliability.

## Frozen question and protocol

The [predeclared E02 protocol](fixtures/e02/protocol.json) asks each condition to take a record ID, read the same synthetic `profile` and `ledger` sources, normalize customer/currency, calculate ready-line minor total and quantities, count hold *lines*, and return exact `profile` and `ledger` source IDs. Only `dev-elm` was available during authoring. The three distinct holdout IDs were supplied in nine new Codex sessions after authoring froze, in order direct → script → CookBook, script → CookBook → direct, then CookBook → direct → script. All conditions used Codex CLI `0.155.0-alpha.9.2`, `gpt-5.6-luna`, low reasoning, `--ignore-user-config --ephemeral --approve-for-me` with normal workspace-write review, the same synthetic service and per-session ceilings of 300 seconds and 32 tool calls. The direct agent was allowed ordinary scripting. The reusable script and Recipe were prepared with one cold authoring session each, plus a cold direct development session.

The independent source and exact expected-output oracle were hashed in `work/evals-2026-09-22/e02-freeze.json` before any authoring or measurement. The source/oracle files remained outside all three authoring projects; no authoring prompt named a holdout ID or gave an expected holdout value. The authoring freeze at `work/evals-2026-09-22/e02-authoring-freeze.json` (SHA-256 `c8b123da4a9fc4fc25bbf8ea2076d96009d86c33170cd1aede8c37f0f85fd6f9`) preceded the measured prompts. Their freeze ledger at `work/evals-2026-09-22/e02/prompt-freeze.json` has SHA-256 `e745370b4197fc410e2bd12fa973ba8f1717ee4bd71bc2b92f5ddb7d85a08568`. The oracle was opened for exact-object grading only after all nine sessions finished. Same-user filesystem access to the synthetic service directory was available and is not a hard blinding boundary; the inspected tool-call logs showed no direct read of `sources.json` or the oracle.

Pass meant exact equality to the complete independent expected JSON object, with no extra fields and both source IDs. Each planned attempt was retained, including failed connection and paid-model usage. No replacement trials or retuning occurred. The separate replay check used a development input, outside the nine-run performance sample. No paid external provider or actual account was used; client subscription dollar cost and any reviewer-side usage remain unknown.

The CookBook case-2 agent wrote both project-connection verification files with **two trailing newlines** when the service supplied exactly one. Both `apr_project connect` attempts returned `FORBIDDEN`, so it never started the Recipe or read either source for that case. Its final response was a failure JSON, not the required task JSON. Its 54.93 seconds, 365,761 input tokens (341,760 cached), 1,739 output tokens and seven tool calls remain in the CookBook totals. The two successful CookBook cases each correspond to one succeeded saved Recipe run with output exactly matching the oracle. This is a first-use/client-handoff failure, not evidence that the registered worker computed a wrong answer. It still fails whole-task acceptance for that condition.

In one separate replay check after a new fixed-attachment MCP bridge connected to the disposable state, repeating the completed `dev-elm` start with the same request key returned the same run ID and succeeded state; the source log remained at ten development reads before and after, with zero new reads. This verifies that completed-request replay path, **not** a service-process restart or effectful exactly-once guarantee.

## Decision and limits

The direct and script conditions met exact output acceptance in this tiny matched sample. CookBook did not, so the launch E02 quality criterion is not met for the evaluated client journey. The CookBook sessions also showed substantially more visible client context and time here; the nine-case pilot, the one failed handshake and unknown subscription pricing do not support a monetary break-even or token-savings claim. Runtime billing alone cannot price client orchestration. The clean next check is a changed and re-frozen client connection flow, followed by **new** heldout cases; this sample must remain a recorded failure rather than being repaired in place. Client model context/cache differed by condition because CookBook adds MCP tools and guides, and same-user fixture access limits blinding. Other platforms, clients, external providers, creative tasks and large-run reliability remain untested.
