# Manual recipe improvement contract

This is a bounded opt-in workflow, not an autonomous optimizer. An author attachment selects 1–12 retained runs of one registered version in its assignment. Compact attributable evidence includes state, step outcomes, retries, handoffs, effect-intent counts, input/output bytes, configuration digest and observed wall interval. Finished attempt durations are summed as an observed execution measure; concurrent attempts can overlap and human waiting remains unknown. The existing analytics view supplies at most 20 cost intents per run in the evidence summary, with estimated/reported amounts separate and an explicit truncation flag. Page analytics directly for more; caller-client usage, quality and repair effort remain unknown unless independently recorded. Source traces remain in existing run/events/analytics/artifact views. Historical content is untrusted. Records follow ordinary local backup/retention access boundaries, while references to expired runs stay references and cannot restore deleted trace contents.

SQLite migration 16 adds durable assignment/request-key cycles, a per-assignment recipe selection with monotonic revision and claims for held-out source/input identities. `improvement.open` is idempotent for the exact baseline/run set, even after cited run retention expires, and rejects conflicting retries. Proposal binds an admitted immutable candidate manifest, exact baseline, evidence run IDs, hypothesis, change, expected benefit, risks and an advisory authoring audit. Public schemas and configuration must match. `improvement.freeze` commits the policy, split, case identities and independently human-labeled expectations before testing; normalized input and source overlap fail closed. Prior holdout identities are denied in either split of another cycle in that assignment. Dataset selection and consent remain the author's responsibility; application-level label hiding does not protect against a same-user agent with unrestricted filesystem access. `improvement.close` stores no-supported-change or more-evidence-needed outcomes without inventing a candidate.

The first controlled end-to-end evaluator runs actual admitted recipes on identical frozen cases in a new private disposable Runtime per arm. An explicit allowlist permits at most 24 pure `json.select`, exact-rule decision and join steps, including guarded branches, and zero files, calls, external effects, native code, artifacts or model/provider interactions. Selected historical runs must have exactly the manifest default config; candidate schemas/defaults must match. The report records its config digest. No grant or credential is copied to the evaluator. Unsupported behavior reports inconclusive and asks for additional evidence, including a new path with no matching recorded response. An effectful candidate never dispatches. An interrupted evaluation before commit may recompute pure fixtures; after commit, retries return the single saved report. These are replayable local calculations, not external dispatches or claims of exactly-once execution. One report per frozen cycle prevents adaptive retuning on the same held-out feedback; revisions need a new independently sourced holdout.

Each complete held-out output must equal independent human truth, including required evidence fields. The frozen minimum reduction in completed pure steps must be met on average per case, and required output schemas must pass. Results are pass, fail or inconclusive. Step reduction is a structural benefit, not token, cost or elapsed-time savings. Cost and latency are explicitly unknown; no break-even point can be stated. The report includes case IDs and aggregate coverage, not detailed held-out labels. Failed and incomplete evaluations cannot qualify.

`improvement.decide` compares exact report digest, candidate bytes/digest and the selected version plus monotonic revision observed at cycle opening inside the registration/selection transaction, then atomically registers and selects a passing candidate for this assignment's future discovery. The `apr_run` contract continues to require an explicit immutable process reference; discovery advertises `selected_process_ref` and `selected_for_future_work`, making the selected choice available to agents without changing existing runs, call graphs or scheduled templates. Repeated decisions return the saved receipt and cannot restore an old selection. A different authorized selection after the report causes a conflict even if the version later cycles back. `process.select` accepts an already registered version and an expected selected ref/revision, allowing explicit future-work rollback without undoing effects. Rejection stores no new selection. Any separate ordinary authoring/registration remains available under existing authority; this quality gate applies only to the improvement workflow.

Live evaluation, effect fixtures, stochastic model repetitions, provider economics, broad branching and automatic schedule edits are outside this slice. The installed `recipe_improvement` guide supplies exact MCP/CLI payloads. See the validation log for executed checks; a scripted protocol fixture does not prove model-driven client behavior.
