# Review and improve a recipe (manual, opt-in)

The attached agent owns the proposal. No background optimizer runs. The current evaluator is deliberately limited to `json.select`, pure exact-rule decisions, guarded branches and pure joins with up to 24 steps. It runs admitted baseline and candidate versions on the same frozen, human-labeled cases in a fresh disposable CookBook runtime with no inherited grants. Selected historical runs must use the manifest's default configuration; another effective configuration needs separate qualification. Unsupported model choices, scripts, effects, artifacts, provider/model calls and missing recorded responses are **inconclusive / additional evidence required**; they are never secretly executed. This synthetic controlled mode proves the mechanism and preserved outputs on those cases, not real-world quality, latency or cost savings. The agent must inspect costs separately; unknown caller or provider usage stays unknown.

Use an author attachment and its `workspace` on every MCP call when applicable. These are complete argument shapes; replace IDs and paths with actual scoped identities. A fixed attachment omits `workspace`.

1. Discover the exact registered version and retained run IDs: `apr_discover {"workspace":"<handle>","query":"synthetic.copy-review"}` then `apr_inspect {"workspace":"<handle>","view":"runs","detail":true}`. Inspect failures as well as successes; expired or unrelated runs cannot be read. Select 1–12 distinct run IDs of the same version and assignment. Read compact counts with `apr_inspect {"workspace":"<handle>","view":"improvement_evidence","process_ref":"sha256:<baseline>","run_ids":["<run-id>"],"detail":true}`; use `run`, `events` and `analytics` for targeted detail. Do not treat success as correctness.
2. Start a durable cycle: `apr_manage {"workspace":"<handle>","action":"improvement.open","request_key":"review-2026-09-21-1","process_ref":"sha256:<baseline>","run_ids":["<run-id>"],"detail":true}`. Save `cycle_id`, `evidence_digest`, and `expected_selected_ref` (null when none). The same key and semantic selection reopens the same cycle; a changed selection is a conflict.
3. Write one candidate manifest in the attached project. For an account-free example fetch `apr_discover {"guide":"recipe_improvement"}` and write its `content.baseline_manifest` and `content.candidate_manifest` objects to project-relative `recipes/baseline.json` and `recipes/candidate.json` with your own file tool. Register the baseline, then start a retained run with its `content.sample_input`. No repository checkout is needed. The candidate removes one redundant selection while preserving both required `answer` and `evidence`. Audit the candidate with `process.audit`. Propose it: `apr_manage {"workspace":"<handle>","action":"improvement.propose","cycle_id":"<id>","candidate_path":"recipes/candidate.json","proposal":{"hypothesis":"one redundant pure selection can be removed","change":"select answer directly","benefit":"at least one pure step per accepted case","risks":"required evidence must remain present","evidence_run_ids":["<run-id>"]},"review":{"steps":{"answer":{"boundary":"deterministic","reason":"exact JSON selection"}},"final_output":{"max_return_bytes":2048}},"detail":true}`. The candidate's public schemas and config must match the baseline. The audit remains advisory.
4. Freeze the acceptance contract **before** evaluating: `apr_manage {"workspace":"<handle>","action":"improvement.freeze","cycle_id":"<id>","policy":{"evaluator_version":"pure-v1","split_method":"independent source IDs","min_step_reduction":1},"development":[{"case_id":"dev-1","source_id":"doc-dev-1","input":{"answer":"A","evidence":"source A"},"expected":{"answer":"A","evidence":"source A"},"provenance":"human"}],"holdout":[{"case_id":"held-1","source_id":"doc-held-1","input":{"answer":"B","evidence":"source B"},"expected":{"answer":"B","evidence":"source B"},"provenance":"human"}],"detail":true}`. Each split supports 1–12 cases, 2 KiB per case; unique case IDs, normalized input and source identities cannot overlap. Held-out inputs/source identities cannot be reused in another cycle in the same assignment. Baseline outputs and generated labels do not count as truth. The response hides held-out cases; a same-user agent with direct filesystem/database access can bypass this application-level hiding.
5. Evaluate once: `apr_manage {"workspace":"<handle>","action":"improvement.evaluate","cycle_id":"<id>","detail":true}`. The returned `report` distinguishes pass/fail/inconclusive, actual baseline/candidate correctness, required-output completeness, step counts, coverage and unsupported work. It makes zero paid calls or production writes. Retrying the same cycle returns the saved report without running fixtures again. Save its exact `report_digest`.
6. Present the report and ask the user to adopt or reject the **exact** candidate. On their instruction, `apr_manage {"workspace":"<handle>","action":"improvement.decide","cycle_id":"<id>","decision":"adopt","candidate_path":"recipes/candidate.json","expected_report_digest":"sha256:<report>","expected_selected_ref":null,"detail":true}`. `reject` uses the same digest/path fields. Adoption registers the frozen version and makes discovery mark it selected for future work in this assignment; ordinary `apr_run` still takes an explicit version. Existing runs and schedules stay pinned. A changed file, changed report, or independently changed selection is rejected. A rollback is an explicit new version choice, and never undoes effects. If no supported change exists or labels are unavailable, save that result without a candidate using `apr_manage {"workspace":"<handle>","action":"improvement.close","cycle_id":"<id>","outcome":"more_evidence_required","reason":"Independent labels have not been gathered."}`; `no_supported_improvement` is the other supported outcome.

The equivalent CLI is `apr improvement --attachment <private-attachment-file> --request-file <json-file>` for a manage payload, or add `--inspect` for an improvement inspect payload. This CLI uses the same scoped service, not owner bypass. `apr_inspect {"view":"improvements","process_ref":"sha256:<baseline>"}` returns ten compact latest cycles; `view:"improvement",cycle_id` returns the redacted report. To explicitly roll back future discovery to an older already registered version, call `apr_manage {"action":"process.select","process_ref":"sha256:<prior>","expected_selected_ref":"sha256:<current>","expected_selection_revision":1}` with the actual selected revision. This requires author access and never changes existing runs or schedules. Inconclusive results call for a refreshed independent dataset or ordinary controlled/live qualification under separate authorization, not a larger silent experiment.
